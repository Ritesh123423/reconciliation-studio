# Reconciliation Studio

A single-file, 100% browser-based tool for bank-vs-books reconciliation and bank statement analysis. Nothing you upload ever leaves your browser — there is no server-side processing or storage of your financial data.

The reconciliation tool itself (`index.html`) is unchanged and still does all of its work client-side. A small Python/Flask service (`app.py`) sits in front of it purely to require login — it only ever sees usernames and password hashes, never the files you work with.

## Features

- **Bank vs books reconciliation**: upload bank statements and your bank book (Excel/CSV), and the tool matches them line by line — exact matches, reversals, batch payments, part payments, and more — with every match explained.
- **Bank statement analysis**: upload bank statements (PDF, scanned image, or the bank's own Excel export) for one client or many. Every line is read and proved against the running balance, then the tool finds inter-bank transfers and reversals and prepares a full analysis (summary, monthly figures, categorisation, Excel export).
- Scanned PDFs are read with an embedded, offline OCR engine (no internet connection needed, nothing uploaded anywhere).

## Running it

**Standalone, no login:** just open `index.html` in a browser — no build step, no server, no installation.

**With login (this repo's hosted deployment):** the app is served through a small Flask service that requires sign-in first.

### Local setup

```bash
pip install -r requirements.txt
export SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
export ADMIN_USERNAME=admin
export ADMIN_PASSWORD="choose-a-real-password"
flask --app app run
```

On first run (only when no users exist yet), the app creates one admin account from `ADMIN_USERNAME`/`ADMIN_PASSWORD`. Sign in at `/login` with that account, then go to `/admin` to create logins for everyone else. There is no default/hardcoded password — if those env vars aren't set and no users exist, nobody can log in until you set them and restart.

### Deploying (Render)

`render.yaml` defines this as a Python web service (not a static site) with a small persistent disk for the login database. Before the first deploy, set these in the Render dashboard for the service:

- `ADMIN_USERNAME`, `ADMIN_PASSWORD` — seeds the first admin account
- `SECRET_KEY` is auto-generated by `render.yaml`

Because the service type changed from `static` to `python`, if this service was originally created from the old `render.yaml`, you may need to recreate it in Render (or delete and re-sync the Blueprint) rather than relying on an in-place update.

## Privacy

Reconciliation logic, file parsing, and OCR all still run entirely client-side, exactly as before — nothing you upload is processed or stored on any server. The login layer only stores usernames, salted/hashed passwords, and an admin flag; it never sees your statements or reconciliation data.
